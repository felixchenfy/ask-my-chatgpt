# ChatGPT PDF Review

Sending content to ChatGPT is the user's decision. If the user has recorded standing consent for GPT messages in an optional local preferences file (not committed; see the plugin README), follow it and do not request per-message permission for content it covers; otherwise send only what the user asked to share. If a tool rejects an action, treat it as an authorization question for the user; this is distinct from operational repair.

If an optional local preferences file (not committed; see the plugin README) exists, read it for the user's standing review destinations and failure-handling choices. When it pre-authorizes autonomous repair, do not ask the user to reload, restart, paste the request again, or reapprove routine repairs; follow [automatic reconnect and maintenance](references/extension-reconnect.md) when repair is necessary. Treat older skill descriptions or chat quotations requiring manual Reload as historical, not as a prerequisite. Coordinate failures with the designated maintenance task when one exists, preserve submission evidence, and continue after a verified repair under the same authorized operation.

Use the `ask_chatgpt` MCP tool supplied by the installed `chatgpt_pdf_review` server. It routes through the configured WebContentAgent project, its loopback task bridge, and WebContentAgent Chrome Companion. By default the launcher resolves the WebContentAgent repository that contains this plugin (`integrations/codex-plugin`), then a sibling `WebContentAgent` checkout; `WCA_PROJECT_ROOT` and `WCA_PYTHON_EXECUTABLE` override the environment. Do not use Codex browser-control tools or the legacy Edge/Playwright server for routine sends. Read [references/local-agent-workflow.md](references/local-agent-workflow.md) before the first send in a task.

Call `ask_chatgpt` once with the exact `question`. Derive a stable, human-readable `session_key` for the logical workflow and reuse it for every continuation. Use a distinct, stable `idempotency_key` for each authorized question: retries preserve it, while a genuinely new authorized follow-up gets its own key in the same session. Include `attachment_path` only when the user requested a PDF or file review. If the user supplied an existing canonical `https://chatgpt.com/c/...` URL, pass it on the first call; the bridge then binds that URL to the session. Use `new_conversation: true` only when the user explicitly asks to start over. Never use `force_send: true` unless the user explicitly asks to resend a blocked request.

Use `thinking_mode: "current"` by default. Map an ordinary request for “max thinking” to `thinking_mode: "prefer_max"`; use strict `thinking_mode: "max"` only when the user explicitly says not to send unless Max is verified. Do not invent a strict requirement from a preference. Report a fallback as unverified Max using the current page setting, never as a Max or Pro selection. If a failed call accidentally used strict mode, coordinate the audited configuration correction in [references/composer-readiness-and-retry.md](references/composer-readiness-and-retry.md); do not just change arguments or keys.

A project conversation may appear at `https://chatgpt.com/g/g-p-<project-id>/c/<conversation-id>`. The bridge recognizes that complete route as an alias of `/c/<conversation-id>` and returns the latter as its durable identity. It does not authorize a project landing page, an arbitrary GPT page, or a different conversation ID. For an already failed call, preserve its original arguments and key; do not rewrite the destination just to retry.

Track conversation URLs across Codex tasks using `%USERPROFILE%\.codex\chatgpt-pdf-review\conversations.json`; read [references/conversation-tracking.md](references/conversation-tracking.md) when creating, naming, resuming, or checking a tracked conversation. The ChatGPT URL is the durable handle; a browser/MCP process does not need to remain alive between operations. A user-supplied `/c/WEB:...` route is provisional: it may be used once to reach that conversation, but never save it as the durable registry URL. Save only the stable canonical `/c/...` URL returned by the bridge; if none is returned, stop without updating the registry.

Treat one `ask_chatgpt` call as the complete send workflow: the local agent validates the destination and optional PDF, saves a private task record outside Git, stages the exact input, records successful submission, waits for a stable assistant response, and returns the response with the canonical URL. Explicit operation keys remain protected across days, and unresolved sends never become retryable merely through age. Reusing a key with changed arguments returns `idempotency_conflict`; reconcile the original arguments rather than changing keys to evade it. Only completed automatic content fingerprints have a 30-minute convenience window. A throttle result opens a 30-minute no-send cooldown. Preserve `duplicate_blocked`, `timeout_after_submission`, or `throttled_cooldown` as returned. Do not repeat a blocked send; continue diagnosis through failure coordination, and resume only under the specific zero-submission or read-recovery rules below.

If the AskGPT workflow has an operational or validation failure, do not merely pause the originating task. Read [references/failure-coordination.md](references/failure-coordination.md): preserve its evidence, contact the designated maintenance task if one exists, coordinate diagnosis and repair in both tasks, and resume the originating workflow when the maintenance task reports a verified resolution. Coordination does not authorize a duplicate send or weaken the recovery rules below.

For `bridge_busy`, preserve the rejected call and coordinate with maintenance without interrupting the existing listener. This rejection occurs before queueing and may have no `task_file`; its zero-submission evidence applies only to this invocation, not to any earlier request with the same key. Follow the bounded continuation rule in [references/failure-coordination.md](references/failure-coordination.md).

For a PDF path-policy rejection, do not infer delivery from the generic adapter error or the absence of a `task_file`. Follow the pre-task validation branch in [references/failure-coordination.md](references/failure-coordination.md): establish where validation failed and check prior durable state before changing an attachment path. Keep the configured allowlist intact.

For a composer-readiness failure or a later user-authorized retry of a failed pre-submission call, read [references/composer-readiness-and-retry.md](references/composer-readiness-and-retry.md). Preserve the actual error and bounded structural evidence; a generic timeout does not identify the page's cause. A safe retry uses the preserved arguments and the same idempotency key, never a new key to evade a block.

The companion prefers an already-open Chrome tab whose normalized URL exactly matches the target canonical conversation. It creates or navigates a managed tab only when no exact match is available. Never reuse a different conversation merely because it is the active ChatGPT tab. A `draft_conflict` preserves existing user text and attachments: coordinate diagnosis, but do not clear or overwrite the draft as a repair.

An attachment conflict with a visually empty composer needs production evidence: native file inputs can retain an earlier submitted file. A retained `FileList` alone proves neither a current draft nor a ready attachment. Follow the read-only diagnostic procedure in [references/composer-readiness-and-retry.md](references/composer-readiness-and-retry.md); keep real draft and upload protection intact.

Submission confirmation can take up to 120 seconds, limited by the remaining preparation budget; this is observation of the same single send, not a retry. For `submission_unconfirmed`, consult [references/submission-confirmation.md](references/submission-confirmation.md). `message_submitted: false` means unconfirmed, not unsent. An unverified `last_observation.candidateMessageId` is diagnostic only and must not be substituted for `submitted_message_id` to enable recovery. A temporary `/c/local-chatgpt%3A<uuid>` route is not a durable conversation identity. Changed message markup requires a verified adapter before consuming the one recovery read; do not read an arbitrary latest answer to test compatibility.

Waiting for a stalled response may briefly foreground Chrome and enable a temporary, target-scoped focus-emulation lease, released when the operation ends. This keeps the document rendering and may show Chrome's debugging banner; it is not another send or proof that the answer is complete. Do not interfere with the active wait by reloading the page or starting a parallel read.

The bridge automatically performs one read-only recovery inside the same `ask_chatgpt` call when a submitted response is unverified or its callback times out, and both a stable canonical URL and `submitted_message_id` are available. Recovery stays bound to that original user message, never an arbitrary latest answer. Treat `completed_after_read_recovery` as success only with `response_extraction_verified: true`. If `automatic_read_recovery_attempted: true`, do not call `read_chatgpt_conversation` again. For an older result without that field, one compatibility read is allowed only with the returned `submitted_message_id` passed as `expected_message_id`. A confirmed send followed by `conversation_mismatch` and `automatic_read_recovery_attempted: false` instead follows the maintenance-owned diagnosis in [references/submission-confirmation.md](references/submission-confirmation.md): verify the preserved identity and unused recovery allowance, then assign one task the bound read. If a verified ID is missing, independent full-turn verification is required before any diagnostic read. This recovery tool must never type, upload, or submit. Never send a follow-up asking ChatGPT to repeat its answer merely to recover text.

Cancellation revokes any not-yet-granted submission permit. A cancellation after the single-use permit was granted can race the actual submit: treat `cancelled_submission_unknown` as ambiguous, never as zero submission, and do not resend. Cancellation after confirmed submission stops waiting; it does not unsend a ChatGPT message.

For an open-ended review with a user-requested lower bound such as “at least 900 characters,” pass that bound as `minimum_response_characters`; do not accept a shorter result. For deterministic extraction requests such as “return every line” or “quote the sentence,” extract the attachment locally when practical. Normalize NFC, line endings, non-breaking/zero-width spaces, surrounding whitespace, and repeated horizontal whitespace in the same way as the bridge. Pass `expected_response_characters` (excluding newlines), `expected_response_lines`, and `expected_response_sha256` whenever they can be computed reliably. The bridge must return `response_unverified`, never success, if any supplied expectation differs. Independently compare the returned text too. Treat any omission, truncation, reordering, or unexplained rewrite as suspicious, then use the single read-only recovery above with the same expectations. Do not require exact deterministic expectations for open-ended reviews whose wording is not expected to match the attachment.

After completion, require `response_extraction_verified: true`, return `response_text` and `conversation_url`, then update the tracking registry. A review workflow is complete only when usable GPT feedback was actually retrieved for the intended revision; check version evidence as described in [references/local-agent-workflow.md](references/local-agent-workflow.md). If Codex edits without that feedback, label the result **Codex-only refinement**; never describe it as GPT-reviewed or GPT-refined. Keep `task_file` private unless the user asks for diagnostics. Do not automate passwords, MFA, CAPTCHA, account verification, or recovery. Do not copy Chrome cookies, credentials, or profile data. Do not silently change the selected ChatGPT model.

If `ask_chatgpt` is unavailable and the error identifies a missing path under `%USERPROFILE%\.codex\plugins\cache\personal\chatgpt-pdf-review\<version>`, run `scripts/repair-installed-cache.ps1` once from the stable plugin source (`CHATGPT_BRIDGE_SOURCE` when configured, otherwise the WebContentAgent checkout's `integrations\codex-plugin` directory). This restores only missing compatibility entrypoints and does not send anything. Retry the original single tool call only after confirming no message was submitted. For any other unavailable-server error, or if repair fails, preserve the startup evidence and contact maintenance through the failure-coordination procedure. Do not silently fall back to browser-control tools, because that route can require action-time confirmation and was replaced by this local-agent workflow.

If the bridge returns `extension_not_connected` or says Chrome Companion did not connect, read [references/extension-reconnect.md](references/extension-reconnect.md). Preserve the exact call and authoritative submission evidence, diagnose with the designated maintenance task, and resume automatically after verified repair when the same-key retry is safe. Do not turn the failure into a user Reload request. A historical `done`, `ready`, or `reloaded` reply may still continue an uncanceled request, but a fresh user action is not a prerequisite for routine recovery.
