# WebContentAgent local workflow

For a published-article review, publish and verify the intended revision at its canonical public URL before sending, as the requested release workflow requires. Compare the returned feedback's concrete claims or quotations with that revision. Verified extraction only proves the reply was retrieved: feedback describing an older figure, metric, or passage is not a completed review of the current article. Preserve that feedback and report the version mismatch. When the authorized review workflow calls for correcting the source context, a genuinely new follow-up may identify the verified deployment URL and already-public relevant text; keep the same conversation/session and treat it as a new request, not an extraction retry. Do not send unpublished or private source as a substitute, or resend an ambiguous submission with a new key. If version evidence remains insufficient, report that the reviewed revision is unverified.

When the requested output is JSON, parse the unchanged returned text strictly and check its requested fields before calling the task successful. `response_extraction_verified` establishes extraction/completion and supplied text constraints, not JSON validity or semantic correctness. Preserve a formatting failure; a lenient parser or a repaired copy is diagnostic only and must not replace the original result. A completed but malformed answer does not justify another send or recovery read.

Companion 0.4.45 excludes observed inline file-citation controls from a detached response tree before selecting text. This prevents citation labels and UI layout from introducing newlines inside JSON strings. `last_observation.responseTextEvidence` records when that path was used. Literal filenames, authored breaks and answer text remain; citation-chip labels are omitted, so request explicit page numbers when needed. The bridge does not fix GPT-authored invalid JSON or promise lossless citation, code or mathematical formatting.

The authoritative route is the `ask_chatgpt` MCP tool using the configured WebContentAgent root: `WCA_PROJECT_ROOT` when set, otherwise the WebContentAgent repository containing `integrations/codex-plugin`, then a sibling `WebContentAgent` checkout. The tool writes private task records under that root's `runtime/state/chatgpt-bridge`, starts a token-protected loopback server on `127.0.0.1:18732`, and waits for WebContentAgent Chrome Companion to operate the user's normal signed-in `chatgpt.com` page. A `bridge_busy` rejection happens before queueing and may not create a record; follow [failure-coordination.md](failure-coordination.md) rather than interrupting the owner.

For a new conversation, call:

```text
ask_chatgpt(question=<exact question>, session_key=<stable-readable-key>, timeout_seconds=900)
```

The default is `thinking_mode="current"`. An ordinary request for max thinking uses `thinking_mode="prefer_max"`. Strict `thinking_mode="max"` requires an explicit instruction not to send unless Max is verified. A fallback preserves the current page setting and must be reported honestly; it does not verify or select Pro. If the caller mistakenly imposed strict mode, follow the audited correction in [composer-readiness-and-retry.md](composer-readiness-and-retry.md) under the original authorization rather than asking the user to choose Pro unnecessarily.

For a strict-mode failure, inspect `last_observation.thinkingEvidence` when present: the reason, observed composer labels, slider description and selection-attempt evidence identify what the adapter could establish. The September 9 observed interface used a Medium/Power slider whose top setting displayed Pro; its internal `data-max` flag was not visible Max verification. Do not equate the highest numeric slider value, Pro, or a model name with the requested Max setting, select a different model, or relax `max` to `current`/`prefer_max` without authorization. A diagnostics update does not make an unsupported mode available. Coordinate a specific UI/mode decision with the source task rather than repeatedly invoking the unchanged request.

For a PDF review, add the resolved absolute `.pdf` path as `attachment_path`. The bridge accepts only configured roots and file sizes from `%USERPROFILE%\.codex\chatgpt-pdf-review\config.json`.

Check that policy before the first call. A repository checkout or worktree is not automatically an allowed upload root. If necessary, stage only the user-approved PDF as a normal file within an existing allowed directory, verify its resolved containment and byte identity, and use that path. Do not widen the allowlist or use a link to disguise an outside path. If a call already failed, use the pre-task validation procedure in [failure-coordination.md](failure-coordination.md) before changing its arguments.

For a follow-up, reuse the same `session_key`; the bridge resolves its persisted canonical URL and managed tab. Pass a user-supplied conversation URL on the first call to bind it to that session. A complete `/g/g-p-<project-id>/c/<conversation-id>` route is normalized to `/c/<conversation-id>`; a redirect between those forms preserves identity only for the same conversation ID. A `/c/WEB:...` route may be used for initial navigation but is provisional and must never be stored as the registry's durable URL. Persist only the stable canonical `/c/...` URL returned after the page resolves. Caller-supplied query strings, fragments, credentials, shares, arbitrary GPT/project landing pages, and temporary chats are rejected.

The Chrome companion first reuses an already-open tab whose normalized URL exactly matches the target canonical conversation, then falls back to the session's managed tab, and creates a background tab only when neither exists. It never substitutes a different active ChatGPT conversation. It preserves existing drafts, fills an empty composer with the exact question, verifies the normalized text and optional filename, submits the ChatGPT form once, records that submission, anchors extraction to that exact submitted user turn, waits for verified completion evidence and stable response text, and returns the response plus canonical URL. Explicit operation keys remain durable; unresolved sends stay blocked regardless of age. Completed automatic content fingerprints retain a 30-minute convenience window. The narrow exception for a later caller-authorized same-key retry requires terminal authoritative zero-submission evidence; read [composer-readiness-and-retry.md](composer-readiness-and-retry.md) before using it. Visible throttling still opens a 30-minute circuit breaker before any later browser action. Temporary tabs created by the companion are closed after success; borrowed user tabs are not.

For an open-ended response with a requested lower bound, pass `minimum_response_characters`. For exact extraction, pass any reliably known `expected_response_characters`, `expected_response_lines`, and normalized UTF-8 `expected_response_sha256`. Completion is scoped to the current assistant turn rather than historical Copy buttons. Read-only recovery also requires the current turn's own Copy action; merely seeing a streaming assistant node is not completion. Character and line constraints keep the extension waiting through long streaming pauses, and the Python bridge independently checks all supplied constraints before allowing `ok: true`.

If a response stalls, Companion may foreground the verified tab once and use a temporary CDP focus-emulation lease for the remainder of that operation. This can show Chrome's debugging banner. Native activation is not enough to guarantee a visible document: a background page can remain stuck on a streaming prefix. The lease is released on completion or error and never changes the prompt, uploads another attachment or submits a message. Visibility is diagnostic evidence, not completion evidence; the normal current-turn and text checks still apply. Do not reload or start a parallel read while the existing call is waiting.

If the send created a stable canonical conversation but response extraction was incomplete or its post-submission result callback timed out, the current bridge automatically performs this operation once inside `ask_chatgpt`. Its internal recovery timeout is 600 seconds in addition to the original send wait; do not mistake the longer-running single call for a missing retry:

```text
read_chatgpt_conversation(conversation_url=<canonical /c/... URL>, expected_message_id=<submitted_message_id>, timeout_seconds=600)
```

This recovery reads only the assistant turn after the identified original user message. Missing or unmounted message identity fails closed; it cannot be replaced by an older answer or another user's follow-up. A standalone user request to read the latest response may omit the identity, but recovering a particular send may not. It never types, uploads, or submits. A successful automatic recovery returns `completed_after_read_recovery` with `response_extraction_verified: true`. If the result says `automatic_read_recovery_attempted: true`, do not perform another read. An older result with no automatic-recovery field and a known submitted message ID may receive one explicit compatibility read. A post-submit `conversation_mismatch` is reported as `failed`, outside the automatic recovery statuses; `automatic_read_recovery_attempted: false` therefore does not mean no message was sent. Use the coordinated diagnostic branch in [submission-confirmation.md](submission-confirmation.md), preserving the original destination and confirmed ID. Never ask ChatGPT to repeat the answer.

Companion uses a random local pairing token generated by `scripts/prepare-companion.ps1` during setup/update, not browser credentials. Its generated extension asset and runtime token file are ignored by Git. Do not print or share them. If pairing is missing, coordinate its scoped repair and connection verification with the designated maintenance task under [extension-reconnect.md](extension-reconnect.md); do not replace it with a fixed public token or ask the user to reload.

If MCP startup fails because an already-open Codex task points into an emptied versioned plugin cache, run `scripts\repair-installed-cache.ps1` from the stable source repository once. The repair copies only missing skill/MCP compatibility files into retained cache-version directories; it does not overwrite intact cache files or contact ChatGPT. Retry a send only when its task record confirms that nothing was submitted.

If the call returns `extension_not_connected`, use [extension-reconnect.md](extension-reconnect.md). Prove submission state, preserve the exact call, coordinate automatic diagnosis/repair with the designated maintenance task, and resume with the same key after verified repair when safe. Do not require a manual Companion reload or fresh user approval.

Do not inspect or move Chrome cookies, credentials, profile data, or unrelated tabs. Do not automate login, MFA, CAPTCHA or account recovery. After installation, a manifest-version change is negotiated by the ChatGPT bridge before it claims a task, and the old service worker reloads itself once. If negotiation cannot reach the new version, maintenance owns diagnosis and authorized repair; do not turn the failure into a user Reload request. Record a genuine external dependency accurately if supported autonomous repair remains impossible.


## Completion and maintenance after the September 6 audit

A response needs the original turn, page completion signals, stable text and all supplied output constraints. Punctuation and repeated-line heuristics cannot veto a completed response, and a minimum character count cannot substitute for page completion or an exact hash. Max selection is scoped to a uniquely identified thinking control and its linked popup; an unrelated selected Max widget is not proof.

The source now includes an isolated Python HTTP → production worker → browser DOM contract test. A passing unit suite or a successful version handshake alone does not prove that a reported live incident was repaired. Preserve hypotheses as hypotheses, particularly when the failed record lacks its observed route.
